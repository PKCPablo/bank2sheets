# Architecture

## Scope

`bank2sheets` is a personal application that uses Open Banking to automatically fetch transactions from one or more bank accounts and sync them to a Google Sheets spreadsheet. In v1 it runs on demand locally (`connect` / `fetch` / `sync`); scheduled sync also runs via `.github/workflows/sync.yml` (monthly on the 1st and the 2nd at 06:00 UTC, `0 6 1 * *` + `0 6 2 * *` + `workflow_dispatch`; the 2nd is an automatic next-day retry after a bank allowance `429` and appends 0 rows (still spending one bank access) when the 1st already appended everything; Actions secrets, never runs `connect` on the ephemeral runner). It never stores bank credentials. The architecture is deliberately simple and extensible so future features (automatic expense categorization, statistics, export to other formats) can be added.

## Stack (ADR-0002)

- Language: Java 21 LTS (Temurin). Java 25 LTS is an acceptable future upgrade.
- Build: Maven single module + `maven-shade-plugin` → executable fat JAR (`java -jar bank2sheets.jar`).
- No application framework (no Spring Boot). Plain Java.
- HTTP: JDK `java.net.http.HttpClient`; JSON: Gson (smallest stable lib, no transitive deps; ponytail decision over Jackson).
- Google Sheets: no official client library — stdlib `java.net.http.HttpClient` + stdlib RS256 service-account JWT (RFC 7523) + Gson. Auth with a Google service account (the spreadsheet is shared with its email). No interactive OAuth.
- Testing: JUnit 5 (minimum).
- Execution: on-demand locally (`connect` / `fetch` / `sync` CLI) plus scheduled sync via `.github/workflows/sync.yml` (monthly on the 1st and the 2nd at 06:00 UTC, `0 6 1 * *` + `0 6 2 * *` + `workflow_dispatch`; the 2nd is an automatic next-day retry after a bank allowance `429` and appends 0 rows (still spending one bank access) when the 1st already appended everything; Actions secrets; never runs `connect` — the ephemeral runner uses `ENABLE_BANKING_SESSION_ID` from secrets). Verified 2026-11-14 via `workflow_dispatch` (issue #4 closed).
- Open Banking providers: the primary provider is **Enable Banking restricted production** (free, personal use, own linked accounts; ADR-0005, 2026-11-13), implemented behind the `TransactionSource` seam and selected by the `ProviderSources` factory. The Enable Banking sandbox was validated 2026-11-13 (`connect`/`fetch`; `sync` twice → 17 then 0 rows) and production real BBVA on 2026-11-14 (`fetch` 171 transactions; `sync` twice → 171 then 0 rows). Salt Edge V6 is a **discarded option** (ADR-0005); its fallback code was removed in GitHub issue #7 (it was sandbox-validated with a fake BBVA provider, but real BBVA was blocked there — `bbva_es` absent from the Service key catalog). Powens (ex Budget Insight) is the only aggregator verified for Trade Republic and is deferred until needed. GoCardless/Nordigen is not viable for new users (stopped onboarding, enterprise-only).

## Configuration / Environment (contract)

Sensitive and per-run values come exclusively from the environment; never commit them.

- `ENABLE_BANKING_APP_ID` — Enable Banking application id (JWT `kid`) (secret)
- `ENABLE_BANKING_PRIVATE_KEY_B64` — base64-encoded PKCS#8 PEM private key for the Enable Banking application (secret)
- `ENABLE_BANKING_REDIRECT_URL` — registered redirect URL: `http` loopback for sandbox (`127.0.0.1`/`localhost`, explicit port, non-empty path) or `https` for production (e.g. the GitHub Pages callback page; the CLI prompts for the pasted callback URL)
- `ENABLE_BANKING_SESSION_ID` — active Enable Banking session id; optional once `connect` has run (persisted to the gitignored `bank2sheets-state.properties`)
- `ENABLE_BANKING_ASPSP_NAME` — optional ASPSP name; default `BBVA` (trimmed; must match the ASPSP name shown in Enable Banking)
- `ENABLE_BANKING_ASPSP_COUNTRY` — optional ASPSP country; default `ES` (ISO 3166 alpha-2, uppercased)
- `ENABLE_BANKING_PSU_TYPE` — optional PSU type; default `personal` (lowercased)
- `BANK2SHEETS_ACCOUNTS` — comma-separated `provider:accountId[:label]` entries to fetch, e.g. `enablebanking:<uuid>` or `enablebanking:<uuid>:Cuenta Nóminas` (optional trimmed label used in the `Cuenta` column; when every entry has a label, `sync`/`fetch` skip the per-account `/sessions`/`/details` accesses); unsupported or unknown providers fail fast; all entries must use one provider per invocation
- `GOOGLE_SERVICE_ACCOUNT_B64` — Google service-account key JSON, base64-encoded (secret)
- `GOOGLE_SPREADSHEET_ID` — target spreadsheet id

Enable Banking contract: Open Banking Gateway API (`https://api.enablebanking.com`), RS256 JWT auth built from `ENABLE_BANKING_APP_ID` + the private key (`kid` = app id, TTL ≤ 1 h). Free restricted-production mode: personal, non-commercial use only, and only the accounts the owner links in the Enable Banking control panel are accessible; ASPSP rate limits apply and sessions need re-authorisation (fresh redirect/SCA) when they expire. The bank's background allowance is roughly 4 accesses per 24 h: once it is spent, `sync`/`fetch` fail with `HTTP 429` / `ASPSP_RATE_LIMIT_EXCEEDED` / `[HUB046]` — the actionable recovery is to wait ~6 hours or until the next day and retry (the scheduled workflow retries automatically on the 2nd), or re-run `connect` to re-consent; do not loop retries, since each attempt spends the allowance. Configuring a label for every `BANK2SHEETS_ACCOUNTS` entry is the opt-in that reduces allowance spend: labelled configs skip the per-account `/sessions`/`/details` accesses. The `/aspsps` lookup and `/auth` flow are parameterized by the three optional ASPSP variables, with BBVA/ES/personal as defaults (BBVA Spain is the validated target; other ASPSPs are configurable but not owner-validated). `connect` uses an `http` loopback listener for sandbox redirects (bound before printing the auth URL) and a paste prompt for `https` production redirects (the `docs/callback.html` GitHub Pages page shows the `code`/`state`). Transaction ids are prefixed `eb:` (Enable Banking) so they stay stable and unique in the sheet.

Local build note (machine-specific, revalidated 2026-11-14): Maven 3.9.9 defaults to JDK 8 (`JAVA_HOME` = `C:\Program Files\Java\jdk-1.8`). `scripts/mvn.ps1` keeps an active JDK 21+ `JAVA_HOME` and otherwise discovers a `jdk-21*` installation under `C:\Program Files\Java` (here Temurin 21.0.12 at `C:\Program Files\Java\jdk-21`), failing with a clear message when none exists.

## Boundaries

- Never store or commit bank credentials or long-lived access tokens; sensitive values come only from the environment (Actions secrets for the scheduled workflow).
- Execution is on-demand local (`connect` / `fetch` / `sync`); scheduled headless sync runs via `.github/workflows/sync.yml` (verified 2026-11-14 via `workflow_dispatch`, issue #4 closed).
- Read source: Open Banking (PSD2) account transaction APIs. Write target: Google Sheets.
- Bank access is isolated behind a `TransactionSource` interface; the provider is selected per invocation by the `ProviderSources.create(AppConfig)` factory, keyed by the provider in `BANK2SHEETS_ACCOUNTS` (one provider per run). When `BANK2SHEETS_ACCOUNTS` is empty, `connect` infers the provider from credentials (Enable Banking) and prints the available account ids/names after consent; `fetch`/`sync` still require accounts. Enable Banking is the only supported provider; unsupported providers fail fast. Adding Trade Republic later means adding a Powens implementation without touching the rest of the pipeline.
- Bank access is read-only by design: only PSD2 AIS consent scopes are requested (`accounts` — covers accounts and balances — and `transactions`); PIS (payment initiation / transfers) is never requested.
- Keep a small pipeline shape (fetch → transform → sync) with room to add categorization/statistics/export stages later.
- Isolation strategy is deliberately informal ports-and-adapters seams, not a formal hexagonal architecture (ADR-0003): bank access behind `TransactionSource` (adding Powens = new implementation, no pipeline changes), HTTP behind `HttpExchange` (tests inject fakes), Google Sheets behind `GoogleSheetsClient` (factory-created), and `Main` as the composition root. Revisit only on concrete pain — second provider → provider-selection factory keyed by config; pipeline growth → extract a use case out of `Main`.
- No web frontend and no database unless a concrete requirement forces one.

## Invariants

- Sync is idempotent per month tab: rows are grouped into tabs titled with the Spanish month name and year (e.g. `Enero 2026`) derived from `Transaction.madeOn()` (never the run date), and existing rows are deduped by exact `TransactionId` against a hidden `_sync` ledger tab (columns `Tab`, `TransactionId`; one `'_sync'!A:B` read per client run plus an in-run id set), so a repeated `sync` appends no duplicates.
- Month tab titles come from a deterministic, locale-independent helper (`GoogleSheetsClient.tabTitle(YearMonth)`: explicit Spanish month list + four-digit year); `YearMonth` remains the routing/dedupe key. The quoted A1 range percent-encodes the space (`'Agosto%202026'!A1:D`) because `URI.create` rejects raw spaces (ADR-0007).
- Each append sorts only the incoming batch by `LocalDate` ascending (stable sort; same-day rows keep provider order) before writing; existing tab rows are never read or rewritten, so a late-arriving transaction with an older date lands at the end of the tab (accepted).
- Month tabs are created on demand: one lazy spreadsheet-metadata GET per run caches the sheet titles (plus one narrowly scoped metadata GET per `sync` for the protection pass); a missing month tab is created with `addSheet`, then the four-column header is written when missing.
- Month tabs for completed months are protected as a whole sheet with `warningOnly: true` on each `sync` (after appends, idempotent by skipping tabs that already have a `protectedRanges` entry); the current and future months stay unprotected, and warning-only protection does not block the service account's appends (ADR-0009).
- Every month tab has fixed columns `Fecha`, `Importe`, `Descripción`, `Cuenta`; `Fecha` is a date-typed cell (ISO `yyyy-MM-dd` input, display per spreadsheet locale; no number format or locale set in code). Rows written by older versions as `DD/MM/YYYY` text stay text — mixed tabs are accepted, no migration runs. A tab whose existing header does not match the four expected cells is rejected with a `Bank2SheetsException` carrying the reset instruction (delete/archive that tab and `_sync`, or use a fresh spreadsheet); no header row is appended to a legacy tab and no in-place migration runs.
- The hidden `_sync` ledger tab is created on demand (hidden `addSheet`, header `Tab | TransactionId`); ledger ids are appended to `'_sync'!A2:B` only after the visible month-tab append succeeds — the visible append always precedes the ledger append, so a ledger failure can cause duplication on a later run but never loses rows. The writer is append-only (`PUT`/`updateValues` was removed with the `F1` backfill).
- The legacy flat first tab is left untouched: no rename, no migration, no deletion. Its rows are not dedupe keys for the month tabs, so the first post-upgrade sync may re-append provider history into month tabs; deleting/archiving it manually is the owner's choice.
- One spreadsheet per year is a manual operational switch, not code: the owner updates `GOOGLE_SPREADSHEET_ID` in `.env` and the Actions secret before the first sync that returns new-year transactions; switching late creates new-year tabs in the old spreadsheet. No new env var or routing logic exists.
- Every appended row carries a `Cuenta` label: the configured label when the entry has one, else the provider account display name when non-blank, otherwise the provider account id. `BANK2SHEETS_ACCOUNTS` may list multiple accounts and all rows go to the same spreadsheet, into the month tab derived from each transaction's date. One bank account per spreadsheet is a deployment pattern achieved by running one instance/fork per account (its own `BANK2SHEETS_ACCOUNTS`, `GOOGLE_SPREADSHEET_ID`, workflow, and secrets) — there is no account-to-spreadsheet routing configuration.
- Visible month rows are appended with `valueInputOption=USER_ENTERED`: `Fecha` is an ISO date string (parsed into a date-typed cell), `Importe` stays a JSON number (numeric cell), and `Descripción`/`Cuenta` are prefixed with one leading apostrophe so they stay literal text. The header row and both `_sync` appends keep `valueInputOption=RAW`.
- Secrets (Enable Banking app id + private key, Google service-account JSON, spreadsheet id) come only from environment variables; nothing sensitive is committed.
- Consent is AIS-only (`accounts` + `transactions`); PIS/transfers are never requested.
- `bank2sheets-state.properties` holds only the provider state id (`enablebanking.session_id`; no credentials, no bank tokens) and is gitignored. A legacy `saltedge.connection_id` may persist in existing state files; it is never read and no migration runs.
- `mvn test` enforces a JaCoCo 80% line-coverage gate (BUNDLE `LINE/COVEREDRATIO >= 0.80`).
- Java 21 is required (`maven.compiler.release=21`).
